## はじめに

最近、金融機関のログイン認証で「メールに届いた画像の内容を選ぶ」方式を見かけます。

実装によっては WCAG の複数の達成基準に適合しません。

本記事は筆者個人の解釈と見解に基づいています。正式な適合判断や法的助言ではありません。

デモを作ったので、ぜひ体験してください。

## 認証の流れ

1. ユーザーがパスワードを入力します
2. メールに認証コードが届きます
3. メールには「画像1の内容：ねこ」「画像2の内容：いぬ」などと書かれています
4. 認証画面で4つの画像ボタンから、メールに書かれた2つを選びます
5. 有効期限は2分です

メール自体はテキストで読めます。問題は、認証画面の画像に代替テキストがあるかどうかだけではありません。メールで示された内容を記憶し、認証画面で画像やボタンから探し出して選択する「記憶・転記」という認知負荷も生じています。

### 悪い例A

認証画面のボタンは画像だけで、`alt` も視覚的ラベルもありません。スクリーンリーダー利用者には、4つのボタンが「ボタン」「ボタン」「ボタン」「ボタン」としか読み上げられません。どれが「ねこ」なのかわかりません。

さらに2分で期限が切れ、延長や警告もありません。

### 悪い例B

画像選択（alt なし）に加えて、テキスト入力の代替手段を置いています。よくある誤解として、「テキスト入力があるので 3.3.8 の『代替手段』例外を満たし、さらに画像認証は CAPTCHA に当たるから 1.1.1 も alt なしで OK ではないか」というものがあります。

しかし、今回の認証は本人確認のための多要素認証（2要素認証）であり、人間とボットを区別する CAPTCHA ではありません。1.1.1 の CAPTCHA 例外は「人間とコンピュータを判別する目的」に限られ、本人確認の認証には適用されません。したがって画像ボタンには通常通り accessible name（アクセシブルな名前、支援技術に読み上げられる名前）が必要です。

結果として、テキスト入力の代替手段は 3.3.8 の『代替手段』例外を満たす可能性がありますが、画像ボタン自体の 1.1.1 は満たしていません。2要素認証なのに CAPTCHA 風の UI を混在させ、代替手段があるから画像のラベルは不要と誤解している例です。

### いい例

画像に `alt="ねこ"` などを付け、視覚的にも「ねこ」と表示します。スクリーンリーダー利用者には「ねこ ボタン」と読み上げられます。時間延長ボタンも置きます。

ただし、alt を付けても、メールの内容を記憶して認証画面で選ぶという認知負荷自体は残ります。3.3.8 の観点では画像認証は「物体認識」の例外に該当する可能性がありますが、メール内容の記憶・転記を伴う認証は認知負荷が大きいため、画像ではなく数字や文字列の認証にするのが望ましいです。

なお、画像の `alt` とボタンの可視テキストが同じ場合、一部のスクリーンリーダーでは「ねこ ねこ ボタン」と重複して読まれることがあります。実装では、可視テキストを `aria-labelledby` で指して画像の `alt` を空にしたり、ボタン全体を `aria-label` で一本化したりする選択肢もあります。`aria-labelledby` の方が、可視テキストを変更したときの漏れを防げます。ここでは alt 属性の存在を明示するため、両方を残しています。

## 該当する達成基準

### 1.1.1 非テキストコンテンツ

認証画面では画像が使われています。画像には意味があり、テキストによる代替が必要です。`alt` 属性や視覚ラベルがない場合、スクリーンリーダー利用者は内容を知ることができません。

なお、今回のような本人確認の認証は CAPTCHA ではありません。1.1.1 の CAPTCHA 例外は、人間とボットを区別する目的で用いられる非テキストのテストに限られます。本人確認の多要素認証にその例外を適用することはできません。

また、画像認証が 1.1.1 の『テスト』例外（テキストで提示すると無効になるテスト）に該当する可能性も議論されます。ただし、その例外であっても『少なくともその非テキストコンテンツを識別できるテキストによる代替』が必要であり、画像ボタンの accessible name を空にしてしまうことは認められません。テキスト入力の代替手段を用意した悪い例Bも、画像ボタン自体の accessible name がないため、多要素認証としての 1.1.1 には適合しません。

### 2.2.1 タイミング調整可能

時間制限がある場合、解除・調整・延長のいずれかが必要です。2分固定で警告や延長もない認証は、この達成基準を満たしません。WAIC の AS テストでは、警告・延長パターン（WAIC-TEST-0121-01）を提供しています。

### 3.3.8 認知機能テスト（最低限）

WCAG 2.2 で追加された達成基準です。認証プロセスで認知機能テストを要求してはなりません。ただし、代替手段・支援メカニズム・物体認識・個人特有のコンテンツの場合は例外です。

今回のデモでは、メールで「ねこ」「いぬ」という認証コードを送り、認証画面でその内容を思い出して選択させています。これは「記憶・転記」を要求する認知機能テストです。画像選択そのものは 3.3.8 の「物体認識」例外に該当する可能性がありますが、メールの内容を記憶して転記させる部分は別の認知負荷として問題になります。問題は画像選択だけではありません。メールの内容を記憶し、認証画面で探し出して選択する「記憶・転記」という認知負荷が生じています。

より厳格な [達成基準 3.3.9: アクセシブルな認証（高度）](https://waic.jp/translations/WCAG22/Understanding/accessible-authentication-enhanced.html) では、「物体の認識」及び「個人特有のコンテンツ」の例外がなく、画像認証そのものが認められにくくなっています。

現行の JIS X 8341-3:2016 は WCAG 2.0 に準拠しており、3.3.8 は含まれていません。しかし次期 JIS 改正では WCAG 2.1 や 2.2 の追従が想定され、画像や絵文字で認証する方式は明確に問題になります。さらに、2024年4月1日の改正障害者差別解消法による合理的配慮の義務は、JIS のバージョンに依存しません。

## ボット対策との関係

認証を複雑にすれば安全になる、と一見思われがちです。しかし、画像のラベルを隠したり、ユーザーにメール内容の記憶・転記を強いたりしても、最新のボットは画像認識や DOM 解析で容易に破ることができます。結果として、被害を受けるのはスクリーンリーダー利用者や認知負荷の高い人だけになりかねません。

ボット対策はサーバーサイド、レート制限、パスキー（FIDO2 / WebAuthn）、機械学習ベースの bot 検知などで行うべきで、認証 UI のラベルを隠すのは誤ったトレードオフです。

## 改善策

- 各選択肢に accessible name を付ける
- 画像ではなく、数字や文字列の認証にする
- 画像を使う場合は必ず `alt` 属性を付ける
- テキスト入力の代替手段を提供する
- 十分な操作時間を確保し、延長ボタンを置く
- OTP アプリ、音声認証、パスキー（FIDO2 / WebAuthn）などの代替認証を検討する
- 多要素認証と CAPTCHA は目的が異なるため混在させず、目的に合わせて適切な方法を選ぶ

## 新しい方向：コピペ不要の自動入力

認証を画像選択ではなく数字や文字列にしても、メールに届いたコードを確認してコピー＆ペーストする手順は依然として認知負荷になります。ここでも新しい技術動向があります。

2026年、Google は Chrome Canary で「Gmail OTP Autofill」機能を試験しています。Gmail にログインした同一プロファイルで、サイトの OTP 入力欄にメールの確認コードを提案するものです。コピー＆ペーストを省き、転記の負荷を減らすユーザーエージェント側の支援例になります。ただし、このフラグはデフォルトでオフであり、安定版ではなく、実機テストでは未動作の報告もあるため、あくまで動向の注記です。

なお、サイト側の適合とは別の話です。たとえ Chrome が自動入力を提案しても、入力欄が貼り付けを拒否したり、パスワードマネージャーや自動入力を妨げたりしていれば、ユーザーは支援を受けられません。3.3.8 で想定される「補助メカニズム」は、コンテンツ側がコピー＆ペーストや自動入力を妨げないことが前提です。また、スクリーンリーダー利用者にとって自動入力がどう通知されるか、手動確認が不要かどうかは未確定です。

同じ動向として、iOS 26 では Gmail アプリの通知から確認コードをキーボード候補に表示する機能が先行して実運用されています。PC 実験より先にスマートフォン側で、メールからの転記負荷を減らす方向が進んでいます。

したがって、画像認証を `alt` 付きの画像にするだけでなく、そもそも数字や文字列の認証にして、さらにコピー＆ペーストや自動入力を妨げない設計にすることが望ましいです。

## まとめ

メールではテキストで書かれた認証コードが、認証画面では画像だけで提示されると、スクリーンリーダー利用者は操作できません。2分の固定時間制限も加わると、1.1.1、2.2.1、3.3.8 の複合的な失敗例になります。

なお、画像に `alt` を付けた「いい例」でも、メールの内容を記憶して認証画面で選ぶという認知負荷は残ります。3.3.8 の「物体認識」例外に該当する可能性はありますが、認証に画像を使うこと自体は推奨されません。金融サービスには高いセキュリティと正しいアクセシビリティ理解の両方が求められ、次期 JIS 改正や合理的配慮の義務を踏まえ、認知に依存する認証を避ける設計が求められます。
